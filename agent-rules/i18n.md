# Internationalization

- Every developer-authored, user-visible string must be complete in every locale
  the application supports. This includes UI labels, states, notifications,
  validation messages, and accessible text such as placeholders, `aria-label`,
  `title`, and `alt`.
- Update all active translation catalogs through the established i18n mechanism.
  Keep interpolation placeholders and their meanings consistent across locales;
  use `useI18n().t(...)` where text is produced outside DOM localization.
- `data-i18n-ignore` is only for runtime/user-provided verbatim content or
  identifiers. Do not use it, checker exclusions, or catalog omissions to
  bypass product-copy translation.
- When adding a locale or changing locale behavior, update locale definitions,
  catalogs, validation, and locale-sensitive formatting together.
- For UI or i18n text changes, run
  `npm --prefix frontend-enterprise run i18n:check` and relevant frontend tests,
  then verify affected states after switching between supported locales.
