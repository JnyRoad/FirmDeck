# Feature Specification: 租户管理端统一知识库管理（knowledge-base-admin）

**Feature Branch**: `feat/knowledge-base-admin`（规格编写时所在分支：`claude/knowledge-base-admin-design-057e6c`；进入开发时按 Git 规则另建 `feat/` 分支）

**Created**: 2026-09-01

**Status**: Draft

**Input**: User description: 租户管理端「统一知识库管理」功能。基于已确认方案与可交互原型（https://claude.ai/code/artifact/4539f582-ac66-4d62-bb50-b07aa3c1f57f，含「设计蓝图」页）落成规格。原型是本规格的交互事实源：凡本文未细述的界面布局、文案与状态流转，以原型为准。

## 背景与问题

租户管理员目前没有统一的知识库管理入口：

- 共享知识库创建后在管理端几乎不可见（无员工上下文时列表把共享库过滤掉），群组页"绑定已有共享库"下拉恒为空。
- 共享库的文档增删改在前端没有任何入口（写入请求未指向草稿版本，服务端拒绝）。
- 未绑定任何群组的共享库无法做任何版本操作（版本操作强制要求团队上下文，管理员也绕不过）。
- 私有知识库只能切换员工作用域后逐个查看，管理员无法回答"租户里一共有哪些知识库"。

本功能在租户管理端新增仅管理员可见的「知识库管理」，统一管理本租户全部知识库（共享 + 私有），并为共享知识库提供 Git 式的多草稿协作、审阅与发布流程。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 管理员总览并管理全部知识库 (Priority: P1)

租户管理员打开侧栏「知识库管理」，无需切换员工作用域即可看到本租户全部共享库与私有库，按类型 / 状态 / 归属员工 / 绑定群组筛选，进入任一知识库详情进行管理；也可直接新建共享库或私有库。

**Why this priority**: 这是所有其他能力的入口；没有它，共享库和私有库的管理路径依然割裂且不完整。

**Independent Test**: 以管理员登录，创建 1 个未绑定群组的共享库、1 个员工私有库，在列表中均可见、可筛选、可进入详情并修改名称；非管理员账号看不到该菜单且直接访问路由被重定向。

**Acceptance Scenarios**:

1. **Given** 租户内存在共享库（含未绑定群组的）与多名员工的私有库，**When** 管理员打开知识库管理列表，**Then** 全部知识库均出现，统计卡显示总数 / 共享 / 私有 / 文档总数，未绑定群组的共享库显示"未绑定群组"提示。
2. **Given** 列表已加载，**When** 管理员按"私有知识库 + 归属员工 = 林晓"筛选，**Then** 仅显示林晓的私有库；按"绑定群组 = 客服一组"筛选，**Then** 仅显示绑定了该群组的共享库。
3. **Given** 管理员点击「新建知识库」并选择"私有"，**When** 未选择归属员工即提交，**Then** 系统阻止并提示必须选择员工；选择员工并填写名称后提交，**Then** 新库出现在列表并跳转到其详情。
4. **Given** 某行的「⋯」菜单，**When** 管理员点击「下线」，**Then** 该库状态变为已下线且成员不可再检索；点击「删除」需二次确认，确认后该库及其群组绑定、授权、默认写入指针一并清除。

### User Story 2 - 共享库草稿协作、审阅与发布 (Priority: P1)

管理员或具备编辑权限的员工在共享库上创建草稿（草稿相当于分支，只有草稿名和"基于哪个正式版"），在草稿工作区上传 / 编辑 / 删除文档；管理员在发布前用 Git 式的审阅编辑器逐块接受 / 拒绝 / 直接修改，然后发布。发布时才分配版本号（默认递进修订号），所有授权成员立即读到新正式版。

**Why this priority**: 共享库当前在前端没有任何内容编辑入口，这是功能缺失而非体验问题；审阅与版本规则是团队协作的安全底线。

**Independent Test**: 在一个共享库上创建草稿、上传一篇文档、修改一篇、删除一篇，用审阅编辑器接受两处、拒绝一处、手动改一处并应用，发布后正式版内容与审阅结果一致，版本号为上一正式版的修订号 +1。

**Acceptance Scenarios**:

1. **Given** 共享库当前正式版为 v1.0.0 且无草稿，**When** 管理员在内容页点「创建草稿」并填写原因，**Then** 生成一个带草稿名（如 draft-7f2c）、基于 v1.0.0 的草稿，内容页切换到该草稿工作区，横幅显示创建者、来源、基线、原因。
2. **Given** 正式版视图，**When** 查看文档列表，**Then** 只显示正式版文档且只读；切换到草稿视图，**Then** 显示草稿新增文档并标注"草稿新增 / 草稿修改 / 草稿删除"，删除标记可一键恢复。
3. **Given** 草稿包含新增 1 篇、修改 1 篇、删除 1 篇，**When** 管理员打开「查看变更」，**Then** 顶部显示三类计数，每篇文档以行级差异展示（删除行红色带删除线、新增行绿色），配对的行内只高亮真正变化的字符。
4. **Given** 审阅编辑器中的某个变更块，**When** 点「接受」，**Then** 该块折叠为带 ✓ 标记的普通文本，不再显示红绿，顶部"已接受 N 处（暂存）"计数 +1，「撤销接受」可恢复；**When** 点「拒绝」，**Then** 该块内容回到基线原文。
5. **Given** 审阅编辑器，**When** 直接在绿色行或普通行上输入、回车、退格、跨行选中后删除 / 输入 / 粘贴，**Then** 文本即时更新且红绿标记整篇实时重算（含中文输入法组合期间不闪烁）。
6. **Given** 审阅编辑器中的红色删除行，**When** 点该行的「↩」，**Then** 原文行恢复：若与某新增行配对则替换该新增行，否则按原顺序插回；**When** 选中若干行后点「撤销选中行变更」，**Then** 与选区相交的变更块整块回到基线。
7. **Given** 已接受全部变更块，**When** 查看顶部状态，**Then** 显示"全部已审阅 / 已接受 N 处（暂存）"，且「应用到草稿」可点击；应用后审阅状态（已接受数、待审阅数）记录到草稿并写入审计。
8. **Given** 一个草稿基于 v1.0.0，正式版仍为 v1.0.0，**When** 管理员发布，**Then** 发布确认框显示"发布后版本号 v1.0.1"（默认修订号递进）与审阅状态，可切换为次版本 v1.1.0 或主版本 v2.0.0；确认后该草稿获得所选版本号成为正式版，审计记录"草稿 X（基于 v1.0.0）合并为 v1.0.1"。
9. **Given** 版本列表，**When** 查看，**Then** 顺序为：进行中草稿置顶（新在前）→ 正式版本按版本号降序 → 已驳回草稿最后；历史正式版可「回滚到此版本」。
10. **Given** 员工 editor 在群聊中已创建但未发布的草稿，**When** 管理员打开该共享库，**Then** 可在版本切换器中看到并进入该草稿、查看变更、发布或驳回。

### User Story 3 - 多草稿并行与变基（Git 式并发协作） (Priority: P1)

两个人各自基于同一正式版创建草稿并修改；其中一个先发布后，另一个草稿的基线已过期。发布时系统提示并推荐「变基」：把草稿变更重放到最新正式版之上，无交集的文档自动合并，双方都改过的文档进入逐行三方合并；变基后草稿名和内容保留、基线更新，发布时获得下一个版本号。

**Why this priority**: 没有这条，团队协作会出现"有人发布后其他人还在旧版本上改"的覆盖事故，或被迫推倒重来。

**Independent Test**: 草稿 A、B 都基于 v1.0.0；A 只改文档甲，B 改文档甲和乙；先发布 A（→ v1.0.1），再发布 B：系统提示基线过期且 1 篇冲突；变基中对甲逐块选择，乙自动合并；完成后 B 发布为 v1.0.2，且 A 对甲的改动与 B 保留的改动都在正式版中。

**Acceptance Scenarios**:

1. **Given** 草稿 B 基于 v1.0.0 而正式版已是 v1.0.1，**When** 发布 B，**Then** 发布框显示"基线已过期"、冲突文档数，并提供「变基到 v1.0.1」（推荐）、「仍然覆盖发布」（红色警示）、取消。
2. **Given** 选择变基，**When** 查看变基预览，**Then** 每篇变更文档标注"可自动合并"或"冲突：正式版与本草稿都修改了此文档"；无冲突时可直接完成变基。
3. **Given** 某篇文档冲突，**When** 打开逐行合并，**Then** 以草稿基线为三方基准，非冲突段直接合并，冲突段两栏对照（草稿 / 正式版），每块可「采用草稿 / 采用正式版 / 两者都保留 / 编辑此段」，底部合并结果带 Git 风格冲突标记且可手动编辑；仍有未解决标记时不能完成合并。
4. **Given** 变基完成，**When** 查看该草稿，**Then** 草稿名不变、内容为合并结果、基线为最新正式版；再次发布不再提示过期，并获得下一个版本号。
5. **Given** 某人发布了新正式版，**When** 其他草稿持有者查看自己的草稿，**Then** 能看到"正式版已更新为 vX，本草稿基于 vY"的提示。

### User Story 4 - 群组绑定与成员权限 (Priority: P2)

管理员在共享库详情中绑定 / 解绑群组、设置默认写入目标，并为每个群组的成员设置权限（未授权 / 只读 / 可编辑草稿 / 可发布），支持批量设置，整表原子保存。

**Why this priority**: 现有群组页已有权限矩阵，但从知识库视角反向管理是统一页的必要闭环；不影响 P1 的内容与版本能力单独交付。

**Independent Test**: 在一个未绑定群组的共享库上绑定"客服一组"，为两名成员分别设 editor / reader 并保存；在群聊中该 editor 可写入草稿、reader 只能读；解绑后两人均失去访问。

**Acceptance Scenarios**:

1. **Given** 共享库未绑定群组，**When** 管理员在「群组与权限」中选择群组并绑定，**Then** 出现该群组卡片，成员默认"未授权"。
2. **Given** 群组卡片，**When** 批量设为 reader 并点「保存权限矩阵」，**Then** 全部成员为 reader；若期间他人已修改该绑定（修订号不一致），**Then** 保存被拒绝并提示刷新后重试。
3. **Given** 两个绑定群组，**When** 将其中一个设为默认写入目标，**Then** 只有该群组带"默认写入"标记。
4. **Given** 绑定群组，**When** 解绑，**Then** 该群组全部成员授权被撤销、默认写入指针（若指向本库）被清除，知识库及版本保留。

### User Story 5 - 私有库统一管理与转共享 (Priority: P2)

管理员在统一页按"知识库 × 归属员工"查看每个私有库，直接上传 / 编辑 / 删除文档（每次写入自动产生新分支版本），查看分支状态（广场基线、分支头、同步状态），从广场同步、发布到广场为模板、回滚；并可通过向导把私有库事务性地转换为共享库。

**Why this priority**: 私有库在员工侧已有完整能力，本故事是把入口收拢到统一页；转共享向导复用现有能力。

**Independent Test**: 在统一页打开林晓的私有库，上传一篇文档后分支头版本 +1；发起转共享，选择来源版本、填写原因、勾选一个群组，完成后源库归档、新共享库出现并已绑定该群组。

**Acceptance Scenarios**:

1. **Given** 私有库详情，**When** 查看内容页，**Then** 顶部标明"当前查看员工 X 的分支头版本 vN（与广场基线同步 / 有分歧）"。
2. **Given** 私有库，**When** 上传或编辑文档，**Then** 立即生效并产生新的分支版本，版本历史新增一条记录。
3. **Given** 私有库与广场基线有分歧，**When** 点「从广场同步」，**Then** 分支头回到基线并标记已同步；**When** 点「发布到广场为模板」，**Then** 广场模板更新为当前分支头。
4. **Given** 转共享向导，**When** 未填写原因即提交，**Then** 被阻止；填写后提交，**Then** 生成带首个正式版的共享库、按勾选绑定群组、源私有库归档并跳转到新库的「群组与权限」页；转换失败时源库保持不变。

### Edge Cases

- 共享库没有任何草稿时打开审阅：提示"此草稿尚无内容变更"或不提供审阅入口。
- 同一草稿被两名管理员同时审阅并应用：后应用者以当前草稿内容为基础重新审阅（应用带乐观锁，冲突时提示刷新）。
- 接受（暂存）后又在同一区域修改文字：撤销接受时若区域已变化，提示无法精确撤销，改用拒绝或直接编辑。
- 草稿删除了一篇文档，而正式版在此期间修改了同一篇文档：变基时视为冲突，由用户选择保留删除或采用正式版。
- 拒绝一篇新增文档：应用后该文档从草稿移除；拒绝一篇删除：应用后文档恢复。
- 版本号已存在的极端情况（如手工数据）：分配时跳到下一个未占用的号。
- 大文档（数千行）审阅：行级对比在用户可接受时间内完成；超出阈值时按文档整体展示"内容已变更"并允许在编辑器中打开。
- 变基预览中"仍然覆盖发布"：必须二次确认并在审计中记录"覆盖了 vX 的变更"。
- 删除共享库时仍有进行中的草稿：二次确认中明确列出将被丢弃的草稿数。
- 非管理员直接访问管理路由：重定向到其默认页面；员工侧「知识库」页面行为不变。

## Requirements *(mandatory)*

### Functional Requirements

**导航与访问**

- **FR-001**: 系统 MUST 在租户管理端侧栏"系统管理"组提供「知识库管理」入口，仅对租户管理员可见；非管理员访问对应路由 MUST 被重定向。
- **FR-002**: 知识库管理页面 MUST 独立于当前选中的员工作用域工作；详情页当前 Tab MUST 体现在地址中，刷新后保持。
- **FR-003**: 现有员工侧「知识库」页面 MUST 保持原有行为不变。

**列表**

- **FR-010**: 列表 MUST 展示本租户全部知识库（共享与私有，含未绑定任何群组的共享库），并提供总数 / 共享数 / 私有数 / 文档总数统计。
- **FR-011**: 列表 MUST 支持按类型（全部 / 共享 / 私有）、状态（上线 / 下线）、归属员工、绑定群组筛选及名称搜索，且 MUST 支持分页。
- **FR-012**: 每行 MUST 显示名称与描述、类型、归属或绑定（私有 = 员工；共享 = 绑定群组或"未绑定群组"提示）、版本状态（共享 = 当前正式版本号与未发布草稿数；私有 = 分支头版本与同步状态）、文档数、状态、更新时间。
- **FR-013**: 每行 MUST 提供操作菜单：编辑、版本管理、群组与权限（仅共享）、转换为共享（仅私有，已归档时禁用）、导出备份、图谱检查、上线 / 下线、删除。
- **FR-014**: 用户 MUST 能新建知识库：选择共享或私有；私有 MUST 指定归属员工；共享创建后 MUST 立即具备一个空的正式版本且无需绑定群组即可管理。

**共享库内容与草稿**

- **FR-020**: 共享库内容页 MUST 提供正式版本与各草稿的视图切换；正式版视图 MUST 只读且不显示草稿新增的文档。
- **FR-021**: 在某草稿视图中，上传 / 编辑 / 删除文档 MUST 只写入该草稿；文档 MUST 标注"草稿新增 / 草稿修改 / 草稿删除"，删除标记 MUST 可恢复。
- **FR-022**: 多个草稿 MUST 可并行存在，且不同草稿对同一文档的修改互不影响；读取侧（群聊、员工检索）MUST 始终只读正式版本。
- **FR-023**: 草稿 MUST 记录创建者、来源（群组或管理员直连）、基于的正式版本、变更原因（必填）；管理员 MUST 能在无群组上下文下创建、发布、驳回、回滚。

**版本规则**

- **FR-030**: 草稿 MUST 只有草稿名与基线，不占用版本号；版本号 MUST 在发布时分配。
- **FR-031**: 发布时版本号默认递进修订号（x.y.Z），用户 MUST 可选择递进次版本（x.Y.0）或主版本（X.0.0）；新版本号 MUST 高于当前最高正式版本号。
- **FR-032**: 版本列表 MUST 按"进行中草稿（新在前）→ 正式版本（版本号降序）→ 已驳回草稿"排序，并标明当前正式版本。
- **FR-033**: 创建草稿、发布、驳回、回滚、变基 MUST 带并发保护（他人已先变更时拒绝并提示）并写入审计流水。
- **FR-034**: 发布 MUST 把正式版本指针移到新版本并对全部授权成员即时生效；驳回 MUST 保留草稿快照供查看；回滚 MUST 可指向任一历史正式版本。

**变更审阅**

- **FR-040**: 草稿 MUST 在内容页、版本页、发布确认框提供「查看变更」，展示文档级新增 / 修改 / 删除计数与逐篇行级差异（对比草稿基线）。
- **FR-041**: 审阅区域 MUST 可直接编辑（新增行与上下文行可输入、换行、合并行；跨行选区可删除、替换、粘贴；兼容输入法组合），差异标记 MUST 随编辑整篇实时重算。
- **FR-042**: 每个变更块 MUST 支持「接受」与「拒绝」：接受 = 暂存，块折叠为带 ✓ 的普通文本且可撤销接受；拒绝 = 该块回到基线原文。整篇 MUST 支持接受全部、拒绝全部、重置为草稿原文。
- **FR-043**: 块内删除行与新增行 MUST 按相似度配对并做字符级高亮；红色行 MUST 提供"恢复此行原文"，绿色行 MUST 提供"删除此新增行"；选中若干行后 MUST 可撤销与选区相交的变更块。
- **FR-044**: 新增文档 MUST 可整篇拒绝（从草稿移除），删除文档 MUST 可拒绝（恢复）。
- **FR-045**: 顶部 MUST 显示待审阅数、已接受（暂存）数、内容是否已修改；「应用到草稿」MUST 在存在暂存或内容改动时可用，应用后 MUST 把内容写回草稿、记录审阅状态并写入审计；发布确认框 MUST 显示审阅状态。

**并发协作（变基）**

- **FR-050**: 发布时若草稿基线落后于当前正式版本，系统 MUST 提示"基线已过期"、给出冲突文档数，并提供「变基」（推荐）、「仍然覆盖发布」（需二次确认并审计）、取消。
- **FR-051**: 变基 MUST 把草稿变更重放到最新正式版之上：仅一方修改的文档自动合并；双方都修改的文档 MUST 进入逐行三方合并，冲突段可采用草稿 / 采用正式版 / 两者都保留 / 手动编辑，存在未解决冲突标记时 MUST 不能完成。
- **FR-052**: 变基完成后草稿名与内容 MUST 保留、基线 MUST 更新为最新正式版，并写入审计。
- **FR-053**: 正式版更新后，其他进行中草稿的持有者 MUST 能看到基线过期提示。

**群组与权限**

- **FR-060**: 共享库详情 MUST 展示已绑定群组（成员数、默认写入标记），支持绑定新群组（成员默认未授权）、设为默认写入目标、解绑（同时撤销该群组全部授权并清除默认写入指针）。
- **FR-061**: 每个群组 MUST 提供成员权限矩阵（未授权 / 只读 / 可编辑草稿 / 可发布），支持批量设置，整表原子保存并带并发保护。
- **FR-062**: 权限语义 MUST 沿用现有三级模型：只读 < 可编辑草稿 < 可发布。

**审计与设置**

- **FR-070**: 共享库详情 MUST 提供审计流水，按动作 / 群组 / 操作者 / 版本筛选并分页。
- **FR-071**: 设置页 MUST 支持修改名称、描述、能力范围，切换上线 / 下线；删除 MUST 二次确认，并连带清理群组绑定、成员授权与默认写入指针。

**私有库**

- **FR-080**: 私有库详情 MUST 标明所查看员工及其分支头版本与同步状态；上传 / 编辑 / 删除 MUST 立即写入并产生新的分支版本。
- **FR-081**: 私有库 MUST 支持从广场同步、发布到广场为模板、回滚到历史分支版本。
- **FR-082**: 私有库 MUST 可通过向导转换为共享库：选择来源版本、名称、描述、原因（必填）、可选初始绑定群组；转换 MUST 事务性完成（成功则源库归档，失败则源库不变）。

### Key Entities *(include if feature involves data)*

- **知识库**：租户内唯一命名的知识容器，类型为共享或私有，具有状态（上线 / 下线）、能力范围；共享库持有"当前正式版本"指针；私有库关联归属员工的分支。
- **版本**：知识库内容的不可变快照。共享库的版本分为草稿（有草稿名、基线、创建者、来源、原因、审阅状态，不占版本号）、正式版本（有语义化版本号、发布时间、来源草稿）、已驳回草稿；私有库的版本是员工分支的头版本序列。
- **文档变更（草稿覆盖层）**：草稿相对基线对某篇文档的新增 / 修改 / 删除；多个草稿对同一文档的覆盖层互不影响。
- **审阅状态**：某草稿上已接受（暂存）与待审阅的变更块计数及最后审阅时间。
- **群组绑定**：共享库与群组的关联，含是否为默认写入目标与修订号（并发保护）。
- **成员授权**：群组内某成员对某共享库的权限等级（只读 / 可编辑草稿 / 可发布）。
- **审计事件**：对知识库的每次治理动作（创建草稿、编辑 / 上传 / 删除文档、审阅调整、发布、驳回、回滚、变基、绑定 / 解绑、权限变更、覆盖发布）及其操作者、群组、版本、原因。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理员无需切换员工作用域，在 1 个页面内即可看到并进入本租户 100% 的知识库（含未绑定群组的共享库）。
- **SC-002**: 为一个未绑定群组的共享库上传第一篇文档并发布，管理员在 5 步以内完成（新建 → 创建草稿 → 上传 → 审阅 → 发布）；现状为不可能完成。
- **SC-003**: 员工创建的未发布草稿，管理员 100% 可在共享库详情中看到并可发布或驳回。
- **SC-004**: 两个草稿修改同一篇文档并先后发布的场景，第二个草稿通过变基与逐行合并完成发布，两方保留的内容 0 丢失。
- **SC-005**: 发布后版本号严格高于此前所有正式版本，版本列表最新正式版始终在正式版区块首位。
- **SC-006**: 审阅编辑器中，接受一个变更块后该块不再显示任何差异标记；全部接受后「应用到草稿」可用率 100%。
- **SC-007**: 含 200 篇文档的租户，列表首屏加载在 2 秒内；单篇 2000 行文档的行级差异在 1 秒内完成展示。
- **SC-008**: 所有治理动作（草稿、发布、驳回、回滚、变基、绑定、授权、删除）100% 有审计记录，且并发冲突时不发生静默覆盖。

## Assumptions

- 页面访问权限只有一档：租户管理员（role = admin）；不为群组 owner 提供本页面（群组 owner 继续使用群组详情页管理绑定与权限）。
- "管理员直连"是共享库的一种来源上下文：管理员在无群组上下文下创建的草稿，其来源记为管理员而非群组；审计中 team 为空。
- 版本号规则采用语义化版本三段式；发布时默认递进修订号，用户可在发布确认框选择次版本或主版本；不提供预发布 / 构建元数据。
- 草稿名由系统生成的短标识（如 draft-7f2c），用户不可重命名；驳回的草稿保留草稿名与快照，不占版本号。
- 审阅编辑器的合并粒度为文档内"行"，字符级仅用于高亮，不做词级自动合并。
- 变基采用"从最新正式版克隆新快照并逐文档重放草稿变更"的语义；未冲突文档自动合并，冲突文档必须由用户逐块解决后才能完成。
- "正式版已更新"的通知形式在本期为站内提示（草稿横幅与发布框提示）+ 审计记录；邮件 / IM 推送不在本期范围。
- 现有员工侧知识库页面、检索调试、OKF 知识图谱可视化、入库任务进度组件在本功能中复用，不做改动。
- 分期：P0 = 用户故事 1–3 与其依赖；P1 = 用户故事 4–5 与列表分页；P2 = 批量归档 / 批量授权、跨库管理搜索、页内检索调试（本规格不覆盖）。
- 依赖现有能力：知识库与文档管理、共享库版本生命周期（草稿 / 发布 / 驳回 / 回滚）与审计、私有库分支操作、私有转共享、群组绑定与权限矩阵。这些能力已存在，本功能扩展其访问方式与协作流程。
- 已知需要补齐的系统能力（供 plan 阶段细化，不构成本规格的实现约束）：租户级全量知识库列表（含筛选与分页）；共享库草稿 / 发布 / 驳回 / 回滚在无群组上下文下的管理员操作；文档写入指向指定草稿；共享库删除连带清理绑定 / 授权 / 默认写入指针；版本号在发布时分配并支持递进级别；版本对比（文档级清单 + 行级差异）；草稿变基与冲突解决结果写回；正式版更新后的过期提示。
